FitLens 是一个拍照识别餐食 / 运动截图热量并追踪每日热量缺口的减肥 App，前端用 Expo SDK 56 + React Native 0.85 + TypeScript，后端是 Node.js Express 调用 MiniMax-M3 视觉模型。

历史上在 v0.4.0 已做过一次"子代理审查全量修复"（commit `a29024e`），本次重新审视 v0.6.0 / v0.6.1 引入的新功能（AI 教练、好友、账号）和老代码可能积累的问题。

## 3. 工作流（三阶段）

### Phase 1 — 并行审计（2 个 Explore 子代理）
- `agent-bug-boundary`：扫 **Bug / 边界 / 错误处理**
- `agent-perf-render`：扫 **性能 / 启动 / 渲染**

每个子代理独立工作，并行启动，互不知道对方结果。每条 finding 强制 schema：

```json
{
  "id": "BUG-001",
  "category": "bug|boundary|error-handling|perf|render|memory|startup",
  "severity": "High|Medium|Low",
  "confidence": "high|medium|low",
  "file": "src/...",
  "line": 42,
  "snippet": "原始代码摘录",
  "evidence": "为什么这是个问题",
  "suggested_fix": "建议怎么改（不实施）",
  "repro_or_bench": "如何复现或量化"
}
```

写入 `_verify/fitlens-audit-2026-07-05/findings-bug.json` 与 `findings-perf.json`。

### Phase 2 — 对抗性复核（1 个 Explore 子代理）
- 读取两个 findings JSON，**不读源码以外**作为初印象
- 然后**独立**逐条打开对应文件、跳转 line、读上下文 30 行
- 每条给 verdict：`kept | downgraded | dropped`
- 输出 `_verify/fitlens-audit-2026-07-05/verified.json`

判定原则：
- `kept`：源码真实存在该问题且分类严重度合理
- `downgraded`：问题真实但严重度被夸大（如标 High 但其实是 Medium）
- `dropped`：代码已修复、不存在、误读、或 confidence=low 且无客观证据

### Phase 3 — 修复实施（1 个 code-simplifier 类型子代理）
- 仅处理 `severity=High` 且 `verdict=kept|downgraded` 的 **bug 类**发现
- 性能 / 渲染类发现**全部不动代码**，只进报告
- 每个 bug 写独立 commit，message 格式：`fix(audit): <一句话描述> (<finding-id>)`
- **不在审计 commit 里混入修复 commit**

修复约束：
1. 最小变更（diff 行数 < 30）
2. 不引入新依赖、不改 package.json
3. 不改公共类型签名 / API 客户端契约
4. 不重构，不改架构
5. 改完跑 `npm run test` 通过

## 5. 风险与边界

|------|------|

| 修复引入回归 | 仅 High bug、每个独立 commit、修复后跑 vitest |
